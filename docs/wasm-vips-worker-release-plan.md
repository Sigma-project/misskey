# アニメ JXL 変換ワーカーの自動解放

作成日: 2026-09-18。対象: Sigma-project/misskey、base `master`。
状態: 実装・ローカル検証済み。Opus 5 とsubagentの実装レビューが収束し、双方承認。PRのCI確認へ進む。

## 要件・制約

- アニメ JXL 変換で使用したワーカーを、変換していない期間に自動で解放する。
- 進行中・待機中の変換を idle 判定で打ち切らない。次の要求では自動的に再作成する。
- 全フレームの読み込み、縮小サイズ、JXL の quality/lossless/effort/distance と返却形式を維持する。
- アニメ変換は wasm-vips 0.0.16 を維持し、rolldown の external 指定を残す。
- 静止画変換、圧縮品質、DB/API/locale、依存バージョンの変更は対象外。
- 開発環境で検証する。本番の Misskey はこの環境では動いていない。

## 確認できた事実

- 現在の `WasmVipsService` は WASM インスタンスの Promise を保持する。
- Emscripten の通常の pthread 終了は Node Worker をプールに戻す。時間による縮小処理は確認できない。
- 本番では RSS 7.5 GiB / em-pthread 552 本から Misskey 再起動後に約240 MiB / 0 本となった。552 本の生成条件とメモリ使用量の内訳は未確定。
- 今回の独立プロセスでの予備実験（Node 26.4.0、wasm-vips の並列度6、1024px・2フレームGIFを640px以下へ3回、lossless/effort9/distance0）:
  - 公開 `vips.shutdown()` 呼出前: em-pthread 6本 / RSS451.9 MiB。呼出3秒後: 6本 / 452.4 MiB。
  - 専用 Node Worker 内で変換: em-pthread 8本 / RSS502.7 MiB。親 Worker の `terminate()` 完了後: 0本 / 289.8 MiB。
- ワーカーの終了で RSS が必ず初期値へ戻ることは保証しない。上記は短い単一試行であり、本番の削減率を予測するものではない。
- 親 Node Worker の作成・終了を3回繰り返すと、各回 em-pthread は0本へ戻る一方、終了後RSSは279.3 / 329.0 / 366.8 MiBだった（初期47.6 MiB）。保持の原因は未確定。
- 同じ変換を専用の子プロセスで3回行う比較では、子のRSSは550.1 / 525.8 / 563.5 MiB、各回の子終了後の親RSSは49.7 / 49.7 / 50.4 MiBだった（初期48.4 MiB）。子プロセス自体が終了するため、そのメモリはOSによって回収される。

## 設計案の比較

| 案 | 利点 | 欠点・確認結果 |
| --- | --- | --- |
| 公開 `shutdown()` と再初期化 | 小さい変更 | Node Worker が残るため要求を満たさない。単純なインスタンスの作り直しは残存リソースを増やし得る |
| 専用 Node Worker に変換を隔離し idle 時に終了 | Node のライフサイクルで内部 Worker と WASM をまとめて破棄できる。依存の非公開構造を変更しない | 入出力転送、要求と終了の競合、ビルド成果物のパス、エラー伝播の管理が必要 |
| 専用の子プロセス | OS 単位でメモリを回収できる | IPC・起動コストと子プロセス管理が増える |
| pnpm patch で idle pool を縮小 | 個別の空き Worker を解放できる | minify された非公開実装への依存と更新時の再検証が必要。WASM 本体の保持は別途残る |

Codex の当初推奨は専用 Node Worker だったが、上記の比較により専用子プロセスを採用する。idle の間に子を終了し、次回要求で再作成する。起動・IPCコピーのコストを受け入れ、OSによる回収を優先する。

## 設計の比較と議論

Fable 5.1 の継続セッション: `653f1bac-ea59-4fa3-a8e6-a5ae81760c14`。設計情報と実測結果を渡して検討しており、Fable がコードを直接調査した、または実装をレビュー済みとは扱わない。

- 第1回: Fable は専用 Node Worker、FIFO、idle 30秒、連続時200件ごとの再作成を提案した。非公開poolへのパッチを避ける点と、変換完了境界で寿命を管理する点は一致した。
- 相違: ワーカー1本あたりの想定使用量を552倍するだけではRSSの主因は確定しない。既存の出力BufferがWASMを保持する不具合とも断定しない。対象はアニメ変換に渡された寸法であり、別経路の静止画上限11648pxではない。
- 第2回への提示: 公開shutdownではNode Workerが残る実測、Node Workerを終了してもRSSが残る比較、子プロセス終了後は親RSSが安定する比較を渡し、子プロセス版への変更を提案した。
- 同時に、常時要求が来る場合に備える100件ごとの再作成案、raw MJS entryをビルド成果物へ含める方法、IPC開始のready通知、入力所有権維持、終了完了を待ってからの再生成を提示した。100件は暫定的な保守値で最適性の実証はない。
- 起動失敗時のbackoff、個々の変換の時間制限、wasm-vipsの並列数変更、非公開poolの診断パッチは、この自動解放修正の必須要素には含めない。
- 第2回回答: Fable は実測を根拠に子プロセスへの変更と第1回の訂正に合意した。親終了への対処、IPC ready、送信エラー、終了イベント、ref/unref、shutdown の実行中要求保護を追加検討した。
- 第3回: Buffer の汎用 structured clone と Node IPC の直列化を区別した。1 MiBのBufferの16 byteビューをv8.serializeすると21 byteとなる実測を提示し、Fableは「必ず背後のArrayBuffer全体が送られる」という指摘を撤回した。入力コピーの追加は行わず、実IPCで範囲と非detachを検証する。
- 第3回で収束: 子プロセス版、30秒idle、成功・失敗を含む100件ごとの再作成、raw MJSと型検証、固定された出力配置、親終了対応に合意。生成失敗は `close` とpid未設定時の `error` を冪等に処理し、`connected` の確認と `send` callbackを実装する。

## 採用方針

- サービスインスタンスごとに子プロセスを最大1つ用意し、要求をFIFOで直列処理する。旧子の終了確認前に次の子を作らない。
- 最終要求完了から30秒要求がなければ終了する。100件処理した場合は待機要求があっても処理境界で終了・再作成する。変換エラーも件数に含む。
- 入力BufferはNode IPCのadvanced serializationで送る。呼出元のBufferをdetachしない。結果はメイン側のBufferとして返し、子の終了後も有効にする。
- 子は初期化完了をreadyで通知する。通常の変換例外はplain objectのエラーで返す。子の異常終了・IPC失敗では当該要求を失敗させ、失敗した変換を自動再試行しない。
- 通常の終了はIPC切断、5秒経過でSIGKILL。Nest app.closeでは待機要求を拒否し、実行中の1件を最大5秒待ってから終了させる。
- このforkはOSの終了シグナルからNest shutdown hookを呼ばないため、子存命中のみ親のexit listenerを登録して子へSIGKILLを送る。子側もdisconnectで終了する。親がSIGKILLされたとき、子が同期変換中ならdisconnect処理は変換が戻ってからとなる。
- 専用MJSはruntime importをNode builtinとwasm-vipsに限定する。JSDocとTSの型参照で検査し、rolldownでは `workers/wasm-vips.mjs` としてemitする。chunk出力をルートに固定し、通常・e2e・watch・Dockerで配置を維持する。
- forkのexecArgvは空にし、親のCLI用loader/inspectを子へ持ち込まない。環境変数は継承する。

## 範囲と限界

- 初期化または単一変換自体が停止したままの場合の時間制限、入力サイズや同時要求数の新たな上限、プロセス全体のRSS上限は追加しない。idle解放は変換中には実行しない。
- キューには元の入力Bufferが保持される。大量の同時要求のメモリを制限する修正ではない。
- 同期変換で親のイベントループが止まっていた処理を子へ移すため、変換中にも親が要求を受け付けられる。バースト時はキューによって親のピークメモリが増え得る。上限導入は既存要求の拒否基準を変えるため、入力制限・過負荷時の応答を含む別の設計対象とする。
- 子の上限1つはサービスインスタンスごとであり、クラスタ全体で1つではない。Nest終了時の最大5秒のdrain待機と最大5秒の強制終了猶予は合計で最大約10秒となる。
- 再起動後の最初の要求にはWASM再初期化の時間がかかる。100件は最適値の実証を伴わない保守的な区切りである。
- NODE_OPTIONSは継承するため、そこにinspectやloaderを指定した環境への影響は残る。

## 実装手順

1. 変換処理と、その子プロセスの寿命管理を分離する。
2. 同じサービスへの変換要求は直列化し、実行中または待機要求がある間は idle 終了しない。
3. 最終要求完了後に idle timer を開始する。新規要求でキャンセルし、終了開始済みの場合は終了完了後に再作成する。100件でも再作成する。
4. 初期化失敗、変換例外、異常終了、アプリ終了で Promise やリソースを残さない。
5. 入力 Buffer の所有権を呼出元から奪わない。返却 Buffer は終了した WASM に依存しない。
6. 通常・watch・e2e ビルドで Worker の実体を配置し、wasm-vips のアセットは node_modules から読む。
7. CHANGELOG に利用者への挙動変更を記載する。

## 実装・検証結果（2026-09-19）

- 終了処理は `exit` と `close` の双方、および pid が未設定の `error` から冪等に確定する。子の終了後に `close` が遅れても、後続要求を待たせ続けない。実行制限環境で `exit` のみ観測されたケースを契機に追加し、単体テストでも再現した。
- `pnpm --filter backend test --run test/unit/WasmVipsService.ts test/unit/WasmVipsProcess.ts`: 20件成功。30秒idle、100件（変換失敗を含む）での再作成、FIFO、起動・IPC・異常終了、親終了、Nest終了を検証した。
- 実際の2フレームGIFをJXLへ変換し、64×64pxの2フレームを別プロセスでデコードして確認した。入力の部分Bufferの範囲・所有権、終了後の返却Buffer、無効入力後の回復も検証した。
- Linuxの `/proc/<pid>/task/*/comm` で変換中の `em-pthread` を確認し、idle後に子PIDが消えることを3回繰り返した。fake timerは親のidle期限を進めるためにのみ使い、変換・子プロセス・内部スレッドは実物を使用した。
- 通常ビルドとe2eビルドに成功。watch設定は自動サーバー起動プラグインだけを外した検証用ビルドに成功。全3種類で同一のMJSアセットを配置し、実際の変換と子の終了を確認した。本番サーバーを起動した検証ではない。
- `pnpm check-dts`: 18ファイル成功。API・entity・migration・locale・依存バージョンは変更していないため、API生成とmigration検査は対象外。追加コードのSPDX、CHANGELOG、wasm-vips externalを確認した。
- 実行環境はmiseのNode 26.4.0。子プロセスの実変換テストは実行制限外で実施した。制限内では外部コマンドのEPERMやJXLデコーダーの失敗が発生し、同じファイル・コマンドが制限外で成功することを確認した。
- ローカルのmisskey-jsビルド済み型が古かったため、既存の生成元からSDKを再ビルドした。API生成元の変更はない。
- 全体 `pnpm lint` は14 workspace成功、frontend-builderだけ既知のOXC型重複で失敗した。AGENTS.mdの既知例外に該当する。追加テスト後のbackend型チェックも成功した。

## 実装レビュー

- subagent初回: 修正必須の指摘なし。FIFO、期限・件数での再作成、終了イベント競合、エラー伝播、Buffer所有権、ビルド配置を確認した。
- Opus 5 初回に対する検証と対応:
  - 出力パス: 通常/watchは各出力ディレクトリ直下の `ApNoteService-*.js`、e2eは直下の `entry.js` にワーカーURLが配置されることを実ビルドで確認した。`built/boot/` 配置を前提とした懸念は該当しない。実アセットの実行テストはパス差し替えを使うため、バンドル側の配置確認と区別する。
  - キュー上限・クラスタごとの子・終了猶予: 上記「範囲と限界」に追記した。要求の拒否方針の新設は行わない。
  - send callbackの遅延エラー: IPCエラーはプロセス全体を無効とみなし、その時点の処理も失敗させる設計。子は無条件に停止するため、pendingの同一性判定を加えても後続要求の失敗は避けられず、差はエラー文言に留まる。追加の同一性判定は採用しない。
  - 出力BufferのWASM参照: 予備実験で709 byte（別条件23604 byte）の出力に対するbacking ArrayBufferも同じ長さだった。共有1 GiBを参照する前提は支持されず、子の終了後も実出力のデコードに成功しているため、追加コピーは採用しない。
  - `worker.failure` の検査: ready成功直後・継続前にIPCエラーとなる場合に到達する。追加テストで、この検査により送信前に拒否できることを確認した。FIFOのdrainは1つなので、stopping待機をwhileへ変更する必要もない。
  - エラーの追加プロパティ: 呼出元はDriveのwarnとproxyの再throwであり、causeや固有プロパティで分岐しないことを確認した。
  - テスト: 予期しないdisconnectと非同期の終了、ready後のエラーを追加。forkのオプション・URLとshutdownの冪等性も確認した。親exitのテストは先行して追加済み。デコード補助プロセスのstdinにerror handlerを追加した。
  - Vitest設定は既にtestTimeout 60秒・maxWorkers 1、unit includeは `test/unit/**/*.ts`。標準のtestコマンドとCIは先にビルドするため、アセット未生成をskipする変更は行わない。所有権はスキップされない実IPCテストで検証する。
  - PRには本計画Docsだけを含め、既存の無関係なuntrackedファイルを含めない。baseはmaster。
- 上記の判断と検証結果を双方のレビュー担当へ返し、再レビューを実施する。
- subagent再レビュー: 追加テストと対応根拠を確認し、未解決の妥当な指摘なしとして承認。
- Opus 5 第2回: 実装上の指摘は解消。URLの `toEqual` 比較がパスを検証しないという1件を検証したが、使用中のVitest 4.1.10の `equals` はURLのhrefを明示比較し、異なるURLの比較も実行結果falseとなった。指摘は現行依存に該当しないためテストは変更せず、実装箇所と実行結果を返す。キュー上限を追加しない判断はエージェントの設計判断であり、レビュー文中の「ユーザー判断」という表記は採用しない。
- Opus 5 第3回: URL比較の指摘と「ユーザー判断」表記を撤回・訂正し、未解決の妥当な指摘なしとして承認。継続セッションは `3a6b3d69-a64e-49dc-9926-bcba23f26a4b`。
